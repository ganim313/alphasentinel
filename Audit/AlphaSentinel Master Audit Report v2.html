Part 4 — My Independent Audit (New Findings Not in External Audits)

🔴 IND-1: Silent Approval Bug via Pre-Seeded conviction_score = 7.0

Location: scripts/run_live_preview.py:344
Severity: CRITICAL

The AgentState is initialized with conviction_score: 7.0. The second-opinion gate checks conviction >= 7.0. If the LangGraph debate graph fails entirely before the research_judge_node runs (LLM error, graph exception, network timeout) and the graph short-circuits, the returned state has conviction_score = 7.0 — which passes the gate.

This means: a trade can be approved with a conviction score that was never actually generated by any agent. A candidate that the judge would have scored 3.0 passes because the graph errored at the right moment.

  • The judge's regex fallback correctly defaults to 5.0 (below the 7.0 gate) — but this only activates if the judge node runs.
  • If the graph errors before the judge node, the fallback mechanism is never reached.
  • No counter or log exists for "conviction score from pre-seed vs from judge."

Fix: Initialize conviction_score: 0.0 (or -1.0) in the state. A gate failure should be a reject, not a pass.

🔴 IND-2: DhanBroker is Completely Non-Functional — Silently

Location: src/execution/order_manager.py:161
Severity: HIGH (v2 note: Recheck v2 frames this identical fact as a positive — "safe by construction... live capital risk is structurally impossible today even if EXECUTION_ENV were flipped by mistake." Both readings are factually consistent; this report keeps the HIGH severity because the risk being flagged is operator false-confidence, not capital loss — see below.)

DhanBroker.place_order() builds the correct Dhan Super Order JSON, logs "DHAN ORDER SIMULATION (NOT SENT TO API)", and then calls PaperBroker.place_order(), storing the result with execution_type = 'DHAN_SIMULATED'. There is no HTTP request to the Dhan API anywhere in the class. The code's own docstring says this is intentional ("Currently disabled to enforce 30-day paper trading phase") — this is a deliberate safety design, not an accidental bug.

The risk this finding actually flags: not capital loss (impossible by construction, as Recheck v2 correctly notes) but operator false-confidence — a developer setting EXECUTION_ENV=DHAN believing they have enabled live trading, when in fact PAPER_TRADING_MODE silently flips to False (see src/config/settings.py's model_validator) while trades are still 100% simulated. Someone could reasonably read "PAPER_TRADING_MODE: False" in a status dashboard and wire real capital based on that flag alone, without reading the DhanBroker source. Fix priority stays HIGH for the "make the flag honest" reason, even though the "prevent capital loss" reason doesn't apply today.

🟠 IND-3: Benchmark Symbol Config/Code Mismatch

Location: src/config/strategy.yaml + src/screening/vcp_screener.py:62
Severity: MEDIUM

strategy.yaml specifies benchmark_symbol: "^CRSLDX" (NSE 500 Index). The code reads this value via QUANT_ALPHA_CONFIG.get("benchmark_symbol", "^NSEI"). If the YAML loads correctly, ^CRSLDX is used — but yfinance may not have historical data for this ticker, causing the Nifty SMA comparison to fail and regime_passed to default to True (pass-through). Additionally, the ML training script computes market_regime using a synthetic equal-weight index (all bhavcopy stocks), while the VCP screener uses ^CRSLDX/^NSEI. These three different "market regime" definitions (training, VCP, drawdown check) are completely inconsistent.

🟠 IND-4: Screener.in Stale Cache is the Real Shariah Risk (Not Hard Fallback)

Location: src/ingestion/screener_scraper.py, fundamentals_cache table
Severity: MEDIUM

External audits worried about the hard fallback passing non-compliant stocks. The Architect confirms the hard fallback actually fails closed (zero total assets → INVALID rejection). But the real risk is different: the fundamentals_cache table has a 7-day TTL. If a company's Shariah status changes (e.g., debt ratio crosses 33% threshold mid-quarter), the cache serves stale "pass" data for up to 7 days. For a system with Shariah compliance as a first-class religious obligation, a 7-day stale compliance window is a design gap.

🟠 IND-5: RSI Algorithm Inconsistency Between Modules

Location: src/screening/mean_reversion_screener.py vs src/screening/ml_features.py
Severity: MEDIUM

  • mean_reversion_screener.py: RSI computed with .rolling(14).mean() (Wilder's original SMA)
  • ml_features.py: RSI computed with .ewm(alpha=1/14, adjust=False).mean() (EWM approximation)

These give different values for the same data. A stock near RSI=30 may be above 30 in the EWM variant (no ML signal) but below 30 in the SMA variant (mean reversion trigger), or vice versa. The rel_rsi ML feature is also computed using the EWM version but compared against the SMA version's output in screening logic — no single canonical RSI exists.

🟡 IND-6: run_scheduler.py is Single-Threaded — One Failed Job Blocks All Subsequent Jobs

Location: scripts/run_scheduler.py
Severity: MEDIUM

The Python schedule library runs jobs sequentially in a single thread. The run_live_preview.py pipeline (which includes sequential Screener.in scraping for up to 100 symbols × 1–3.5s each = up to 350 seconds) could block the scheduler loop. If a job overruns its slot, the next scheduled job is delayed or skipped entirely. There is no job timeout, no threading, and no skipped-job alerting.

🟡 IND-7: Holiday List is Hard-Coded for 2026 Only

Location: src/utils/holidays.py
Severity: LOW-MEDIUM

HARDCODED_NSE_HOLIDAYS only covers 2026. The sentinel fires every 15 minutes during market hours and uses is_nse_holiday() for gating. In 2027, the list expires silently — the sentinel will fire on NSE holidays, attempting live quotes that return empty. No startup warning is generated when the current year has no holiday data.

🟡 IND-8: portfolio_allocation_pct Stored Against Initial Capital, Not Current Equity

Location: src/execution/order_manager.py:94
Severity: LOW

The stored portfolio_allocation_pct in the positions table is calculated as (executed_price × qty) / ALGO_ALLOCATED_CAPITAL. After a 20% portfolio drawdown, a ₹1L position is stored as "10% allocation" but represents 12.5% of actual current equity. The risk arbiter uses mark-to-market equity for sizing but the stored allocation percentage misleads any reporting or dashboard display.

🟠 IND-9 🆕: Three Mutually Inconsistent "Drawdown"/"Sharpe" Definitions Across the Codebase

Location: scripts/run_drawdown_check.py, scripts/run_evaluator.py, research/backtest_harness.py
Severity: MEDIUM-HIGH
Source: originally Recheck v2 §3.4/3.5 — elevated here to its own finding because it directly undermines trust in every number the dashboard shows, and was previously only implicit inside the generic T2-1 recommendation.

Three different modules each compute risk/performance metrics with a different, non-reconcilable methodology:

  1. run_drawdown_check.py — peak-to-trough percentage drawdown against an all-time high-water-mark, on total equity = capital base + all-time realized PnL + unrealized PnL.
  2. run_evaluator.py — absolute rupee figure, computed only from cumulative realized PnL of closed trades. Ignores open positions and the capital base entirely. Its "Sharpe Ratio" is mean(per-trade return %) / std(per-trade return %) — not annualized, not time-indexed. A real Sharpe ratio is computed on a periodic (daily) equity-curve return series and annualized by ×√252. Per-trade dispersion and annualized time-series dispersion are different statistics on different scales; labeling this "Sharpe Ratio" on a dashboard invites benchmarking it against the conventional "Sharpe > 1 is good" heuristic, which does not apply here.
  3. research/backtest_harness.py — a third, presumably equity-curve-based methodology, used only offline and never reconciled with the other two.

Why this matters operationally: if someone reads "Max Drawdown: ₹5,000" on the dashboard and mentally checks it against the "halt if drawdown ≥ 6%" circuit-breaker rule, they are comparing two numbers that don't share a denominator, an inclusion set, or even a unit. There is no single shared "portfolio state" module that Sharpe/drawdown/exposure calculations all pull from — every new consumer reinvents its own version, which is exactly the class of bug that caused the original (already-fixed) ADTV mismatch this system has already been burned by once.

Fix: see Part 9.7 for the exact shared-module specification.

9.2 (T0-2) ML Retrain — Purged K-Fold with Embargo, and the AUC Gate

⚠️ Do not run this until the models/xgboost_global_meta.json provenance question in the caution box at the top of this document is resolved — you need the current AUC/row-count to know whether this is urgent-critical or merely due-diligence.

Why a single 80/20 split is insufficient: one split gives one point estimate of out-of-sample AUC with no variance information — it can pass 0.53 by chance even if the true skill is ≈0.50. Purged K-Fold with embargo (López de Prado) gives a distribution of out-of-sample AUCs and prevents two specific leakage channels: (a) a training sample whose label window overlaps a test sample's feature window, and (b) serial correlation letting the model "see the future" through adjacent-day autocorrelation.

Algorithm:

Let the dataset have $N$ chronologically-ordered unique trading dates ${d_1, \dots, d_N}$, label horizon $h = 5$ (trading days, matching the FwdRet_5d target), and $K = 5$ folds.

$$ \text{fold_size} = \left\lfloor \frac{N}{K} \right\rfloor $$

For fold $k \in {1, \dots, K}$:

  1. Test set $= $ dates in $\left[ d_{(k-1)\cdot\text{fold_size}+1},\ d_{k\cdot\text{fold_size}} \right]$.
  2. Embargo zone $=$ the $h$ dates immediately before the test set's start and the $h$ dates immediately after the test set's end (a label computed on day $t$ uses data through $t+h$, so any training row whose label window overlaps the test window must be purged in both directions, not just before it).
  3. Train set $=$ all dates not in (test set ∪ embargo zone).
  4. Fit XGBClassifier(booster='dart', tree_method='hist', monotone_constraints=(1,-1,1,-1,1,1)) on train, predict probabilities on test, compute $\text{AUC}_k$.

$$ \overline{\text{AUC}} = \frac{1}{K}\sum_{k=1}^{K} \text{AUC}k, \qquad \sigma{\text{AUC}} = \sqrt{\frac{1}{K-1}\sum_{k=1}^{K}(\text{AUC}_k - \overline{\text{AUC}})^2} $$

Validation gate (replaces the current single-AUC check): $$ \text{Serialize model} \iff \overline{\text{AUC}} - \sigma_{\text{AUC}} > 0.51 \quad \text{(one-sided, conservative — penalizes high-variance folds, not just a low mean)} $$

Pseudocode:

from sklearn.model_selection import BaseCrossValidator
import numpy as np

class PurgedKFoldEmbargo(BaseCrossValidator):
    def __init__(self, n_splits=5, embargo_days=5):
        self.n_splits = n_splits
        self.embargo_days = embargo_days

    def split(self, dates_sorted_unique):
        n = len(dates_sorted_unique)
        fold_size = n // self.n_splits
        for k in range(self.n_splits):
            test_start = k * fold_size
            test_end = min((k + 1) * fold_size, n)
            embargo_lo = max(0, test_start - self.embargo_days)
            embargo_hi = min(n, test_end + self.embargo_days)
            test_idx = np.arange(test_start, test_end)
            train_idx = np.concatenate([
                np.arange(0, embargo_lo),
                np.arange(embargo_hi, n)
            ])
            yield train_idx, test_idx

9.6 (T2-6 / IND-5) Canonical RSI — Wilder's Exponential Smoothing

Defect: mean_reversion_screener.py uses .rolling(14).mean() (simple moving average of gains/losses); ml_features.py uses .ewm(alpha=1/14, adjust=False).mean() (exponential smoothing). These are different formulas that diverge meaningfully near threshold values (e.g., RSI≈30).

Canonical formula (Wilder's original, 1978) — use this everywhere:

$$ \Delta_t = P_t - P_{t-1}, \qquad U_t = \max(\Delta_t, 0), \qquad D_t = \max(-\Delta_t, 0) $$

$$ \overline{U}t = \begin{cases} \dfrac{1}{n}\sum{i=1}^{n} U_i & t = n \text{ (seed)} \[4pt] \dfrac{(n-1),\overline{U}_{t-1} + U_t}{n} & t > n \end{cases} \qquad \text{(equivalently: EWM with } \alpha = 1/n\text{, adjust=False, seeded by the first SMA)} $$

$$ RS_t = \frac{\overline{U}_t}{\overline{D}_t}, \qquad RSI_t = 100 - \frac{100}{1 + RS_t} $$

with $n = 14$. This is exactly .ewm(alpha=1/14, adjust=False) provided the EWM is seeded with a plain 14-period SMA of the first 14 gain/loss values, not with the first single observation (pandas' adjust=False EWM without explicit seeding starts from the first observation, which is a subtly different — and common — implementation error).

Fix:

# src/utils/technical_indicators.py (NEW — single canonical implementation)
def wilders_rsi(close: pd.Series, period: int = 14) -> pd.Series:
    delta = close.diff()
    gain = delta.clip(lower=0)
    loss = -delta.clip(upper=0)
    avg_gain = gain.ewm(alpha=1/period, adjust=False, min_periods=period).mean()
    avg_loss = loss.ewm(alpha=1/period, adjust=False, min_periods=period).mean()
    # Seed correction: overwrite the first valid value with a plain SMA to match Wilder's exact recursion
    avg_gain.iloc[period] = gain.iloc[1:period+1].mean()
    avg_loss.iloc[period] = loss.iloc[1:period+1].mean()
    rs = avg_gain / avg_loss.replace(0, np.nan)
    rsi = 100 - (100 / (1 + rs))
    return rsi.fillna(100)  # RS undefined when avg_loss=0 means pure uptrend -> RSI=100

$$ \rho_{i,j} = \frac{\sum_{t=1}^{60}(r_{i,t} - \bar r_i)(r_{j,t} - \bar r_j)}{\sqrt{\sum_{t=1}^{60}(r_{i,t}-\bar r_i)^2}\sqrt{\sum_{t=1}^{60}(r_{j,t}-\bar r_j)^2}} \qquad \text{(Pearson correlation of daily returns)} $$

$$ \text{Reject new candidate } i \iff \max_{j \in \text{OpenPositions}} \rho_{i,j} > 0.65 $$

def check_correlation(candidate_symbol: str, open_symbols: list[str], threshold: float = 0.65) -> tuple[bool, str]:
    if not open_symbols:
        return True, "No open positions to correlate against."
    with get_read_connection() as conn:
        returns_df = conn.execute(f"""
            SELECT symbol, trade_date, close_price / LAG(close_price) OVER (PARTITION BY symbol ORDER BY trade_date) - 1 AS ret
            FROM bhavcopy_daily
            WHERE symbol IN ({",".join(["?"]*(len(open_symbols)+1))})
              AND trade_date >= (SELECT MAX(trade_date) FROM bhavcopy_daily) - INTERVAL 90 DAY
        """, [candidate_symbol] + open_symbols).df()
    pivot = returns_df.pivot(index='trade_date', columns='symbol', values='ret').tail(60).dropna()
    if candidate_symbol not in pivot.columns or len(pivot) < 30:
        return True, "Insufficient overlapping history — cannot compute correlation; allowing (fail-open here is acceptable, this is a soft guard not a compliance gate)."
    corrs = pivot.corr()[candidate_symbol].drop(candidate_symbol)
    max_corr_symbol = corrs.abs().idxmax()
    max_corr = corrs[max_corr_symbol]
    if abs(max_corr) > threshold:
        return False, f"CORRELATION_BREACH: {max_corr:.2f} with open position {max_corr_symbol}"
    return True, f"Max correlation {max_corr:.2f} with {max_corr_symbol} — within limit."

9.9 (T2-5) Triple-Barrier Labeling (replaces the current single 5-day-forward-return binary label)

Current label (per PRD F-06): $$ y = \mathbf{1}\big(\text{FwdRet}{5d}(\text{Stock}) > \text{FwdRet}{5d}(\text{Nifty500})\big) $$ This ignores path — a stock that stops out on day 2 and then recovers by day 5 gets labeled a "win," which the actual trading system would never have realized (it exits at the stop). Triple-barrier labeling (López de Prado, Advances in Financial ML, ch. 3) fixes this by labeling based on which of three barriers is touched first.

Algorithm: for each candidate entry at time $t_0$ with entry price $P_0$ and $\text{ATR}$ at entry:

  • Upper barrier: $P_0 + 2.0 \times \text{ATR}$ (profit-take, matches T2-5's spec)
  • Lower barrier: $P_0 - 1.5 \times \text{ATR}$ (stop-loss — reconcile this multiplier against the 1.5/1.8 ATR discrepancy flagged at the top of Part 9 before hardcoding)
  • Vertical barrier: $t_0 + 5$ trading days (time-out)

$$ y = \begin{cases} +1 & \text{if upper barrier touched first (within } [t_0, t_0+5]\text{)} \ -1 & \text{if lower barrier touched first} \ \text{sign}(P_{t_0+5} - P_0) & \text{if neither touched (vertical barrier hit — label by sign of terminal return)} \end{cases} $$

def triple_barrier_label(ohlc_window: pd.DataFrame, entry_price: float, atr: float,
                          upper_mult: float = 2.0, lower_mult: float = 1.5, max_days: int = 5) -> int:
    upper = entry_price + upper_mult * atr
    lower = entry_price - lower_mult * atr
    window = ohlc_window.head(max_days)
    for _, row in window.iterrows():
        if row['high_price'] >= upper:
            return 1
        if row['low_price'] <= lower:
            return -1
    terminal_ret = window['close_price'].iloc[-1] - entry_price
    return 1 if terminal_ret > 0 else (-1 if terminal_ret < 0 else 0)

def compute_monthly_drawdown(conn, today: date) -> float:
    month_start = today.replace(day=1)
    # Equity at month start = capital base + all realized PnL from exits BEFORE this month
    equity_at_month_start = capital_base + conn.execute(
        "SELECT COALESCE(SUM(realized_pnl),0) FROM positions WHERE exit_date < ?", (month_start,)
    ).fetchone()[0]
    # Current equity = capital base + all realized PnL to date + current unrealized
    current_equity = capital_base + conn.execute(
        "SELECT COALESCE(SUM(realized_pnl),0) FROM positions WHERE status IN "
        "('CLOSED','STOPPED_OUT','TARGET_REACHED','TARGET_1_TRIMMED')"
    ).fetchone()[0] + conn.execute(
        "SELECT COALESCE(SUM(unrealized_pnl),0) FROM positions WHERE status IN ('OPEN','TARGET_1_TRIMMED')"
    ).fetchone()[0]
    drawdown_pct = max(0.0, (equity_at_month_start - current_equity) / equity_at_month_start * 100.0)
    return drawdown_pct

This automatically resets to 0% at the first trading day of each month (since equity_at_month_start becomes current_equity at that instant) — no explicit "reset" cron job needed, which avoids adding another schedulable failure point.
